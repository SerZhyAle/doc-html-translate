# Proposal: DOC-EXTERNAL-QUALITY for a single-page product site

- **To:** the owner of `DOC-EXTERNAL-QUALITY` 0.9 draft (catalog folder `documentation-quality/`, owner
  FastMediaSorter Android)
- **From:** doc-html-translate, consumer (pointer [`../DOC-QUALITY.md`](../DOC-QUALITY.md), ticket 49)
- **Date:** 2026-09-26
- **State:** drafted in this repository because the catalog was not reachable from the session that wrote
  it. To be filed as `documentation-quality/PROPOSAL-2026-09-26-doc-html-translate.md`; this copy is then
  replaced by a line in the pointer naming the filed file.

The product's published documentation is one static page per author language (`docs.html`,
`docs.ru.html`, `docs.uk.html`), a landing in thirteen languages and four policy pages - 18 pages in all.
Everything the rules ask for that a page can carry is now carried and gated (ticket 49). Four places
read as if they assume a documentation portal; each item says what this site does instead and asks the
contract to say whether that conforms, rather than this repository recording a local waiver.

## Item 1 - rule 2, the search index

The rule's build clause expects a search index beside the rendered pages. Here the whole manual of one
language is one page: the reader's find-in-page reaches every word, and a subject index (`#subject-index`,
gated to reach every section) and a glossary (`#glossary`) sit on the same page. A search index over three
single-page manuals would index the thing find-in-page already covers, and would be one more generated
file to keep equal to its source.

**Asked:** state a threshold - a search index is required when one language's documentation spans more
than one page - or name "one page per language with a subject index" as a conforming form.

## Item 2 - rule 1, task orientation without a portal

A portal splits tasks into pages; this site keeps them as sections of one page (editions, recommended
workflow, quick start, reference, sending logs), reachable from the subject index and linked from the
landing. **Asked:** say that task sections with anchors on one page conform, so a single-page product is
not pushed toward a portal it has no content for.

## Item 3 - rule 6, a step that happens outside the product's pages

The free workflow's third step is the browser's own "Translate page" menu. A capture of a page cannot
show browser chrome, and a hand-made screenshot of another vendor's UI goes stale with every browser
release and differs per browser and language. Steps one and two carry the product's own captures (the
store screenshots, regenerated by script, one per interface language). **Asked:** allow a step performed
in third-party UI to be described in text with its menu name, and say so in the rule, rather than each
consumer recording its own exception.

## Item 4 - rules 3 and 5, two measures worth fixing in the contract

- **Fingerprint form (rule 3).** This repo stamps each localized page with
  `<!-- l10n-source: <english page> sha256:<16 hex> -->`, the hash of the source page's English title,
  description and main text. A stale stamp is an advisory (exit 3), a missing one a failure. If the
  contract names one form, the family's sites can share one checker; this one is offered as that form.
- **Length unit (rule 5).** "60 characters" is read here as 60 Unicode code points after entity decoding.
  Counted in bytes, a Hindi or Bengali title fails at a third of its visible length, and counted over
  the source an `&amp;` weighs five. The adoption scan here reported 14 of 18 titles over the limit; the
  code-point count of the same pages gives 11, plus 6 over-long titles that the in-page pages switch in by
  script. Two honest scans disagreeing is the unit left unstated. **Asked:** say code points.
