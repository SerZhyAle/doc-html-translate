| 2026-07-17 01:45:00 | extension/src/viewer.js | Extension: 100-page chunks + page prefetch | Corrects the assumption the chunking was built on. Chrome's translator does **not** pick up pages appended after it ran: whatever was not in the DOM when the reader pressed "Translate page" stays in the source language, and they have to toggle back to the original and translate again. So every chunk boundary costs the reader an interruption, and the design goal is the opposite of what the code's comments claimed - **fewer and bigger** chunks, not smoother small ones. `PAGE_CHUNK` 50 -> 100, `CHUNK_LEAD` 2 -> 5 (a bigger chunk takes longer to build, so start it further from the edge). Page fetching now keeps `PAGE_LOOKAHEAD` (8) requests outstanding to the pdfjs worker, consumed in page order, instead of awaiting `getPage` + `getTextContent` one page at a time - which left the main thread idle during each worker round trip and the worker idle while the main thread built DOM. Measured in Node (a lower bound: Node has no real worker thread, so the overlap is smaller than in a browser) over a 609-page text PDF: 158ms -> 108ms for 100 pages, **1.46x**, byte-identical output (5117 text items both ways). The stale comments claiming a one-shot insert lets "the translator absorb" a chunk are corrected: the one-shot insert is worth keeping, but for layout cost, not translation coverage. **Measured, not fixed:** on the 2304-page scan that prompted all this, page fetching was never the bottleneck - it runs at ~2100 pages/s and the file has **no text layer at all** (0 text items; pdftotext agrees, and pdfcpu finds exactly one image per page). Its slow render is `appendPdfImages`, which decodes each page's raster (or rasterizes the page) inline in the render loop when "Use OCR for images" is on. Image *extraction* is eager while *recognition* is lazy - a mismatch worth its own ticket. |
